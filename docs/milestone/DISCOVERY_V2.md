# Discovery record: DEFINIT v2

Generated by `node scripts/gen-discovery.mjs`. Numbers come from the raw records named
in each item; where a record does not exist the item says UNKNOWN.

## 1. Sponsor primitive

Stage-bound internal messages (`emit(on='finalized')`) and the protocol lifecycle
projection (`gen_getTransactionLifecycle`). A message pinned to the finalized
stage is not a call the emitting contract makes. It is a child transaction the
protocol creates, from the deciding transaction, after that transaction survives
its appeal window.

## 2. Observed constraint

Three measurements, all on GenLayer Studio Next (Studio-dev) (chain 61997):

- **E1 delivery timing.** 6 recorded decision(s) across 2 full reproduction(s). In each, the finalized message arrived as a child transaction triggered by the deciding transaction, created 0 to 1 second(s) after the appeal deadline (median 0). The appeal window was 30 second(s). Evidence: `docs/evidence/milestone/spike/repro-1/summary.json`, `docs/evidence/milestone/spike/repro-2/summary.json`.
- **E5 sender truth.** The sink recorded the emitting contract's address as the sender of every delivered message and the externally owned account's address for a direct call. Evidence: `docs/evidence/milestone/spike/repro-1/e5-direct-e5.json`, `docs/evidence/milestone/spike/repro-2/e5-direct-e5.json`.
- **E6 v1 differential.** v1's vault accepted the funder's `settle` (execution FINISHED_WITH_RETURN, vault status SETTLED) while the promotion transaction's lifecycle read Accepted with resolutionAction NoOp. The settle was decided at 1792238350, 12 second(s) before the promotion's appeal deadline (1792238362). Evidence: `docs/evidence/milestone/spike/e6-h1-v1-run2.json`.

Additional measured facts that shape the build:

- **E2 appeal.** Appealing inside the window created a new decision (decisionId changed from 1 to 2). Lifecycle: 2s Pending | 11s Accepted | 46s Finalized. The finalized message was created at 1792236939 against a final appeal deadline of 1792236937. This run does not show the window being extended; that is stated plainly rather than inferred.
- **E3 accepted-stage repetition.** UNKNOWN. `emit(on='accepted')` raised an execution error in the VM under the pinned runner, with and without a value argument (observation O5 in `findings-session1.json`), so repeated accepted-stage delivery could not be observed. The docs say it can repeat; this record neither confirms nor denies it.
- **E4 underfunding.** A child budget below the network's minimum was rejected at submission with `AllocationLifecycleBudgetInsufficient` for each budget tried, so gross underfunding cannot lock value in. A funded child that fails at execution is different: the parent ended FINALIZED / FINISHED_WITH_RETURN, the child ended FINALIZED / FINISHED_WITH_ERROR, and the sink recorded 0 entries. The parent succeeds and the effect is not applied.
- **C6.** A transaction that ended FINISHED_WITH_ERROR still reached Finalized (see `findings-session1.json`, O3).
- **Fee allocations.** Each emitted message needs one allocation keyed by recipient and target method name. Two messages to the same method collide (`AllocationDuplicateKey`), so the two stages must target different methods.

## 4. Why existing approaches do not solve it

- **Status polling.** Accepted and Finalized are different protocol states, and a successful status is not a successful execution (O3).
- **Final-scope reads.** Measured in v1 and recorded in `docs/LIMITATIONS.md`: the in-VM final-scoped read never returns, and the client-scoped one resolves against transaction finality.
- **Fixed timers.** v1's 120 second constant has no relationship to the protocol window (30 second(s) here), and an appeal creates a new decision with its own deadline.
- **v1 itself.** E6: its vault accepted a release against a decision that was still appealable.

## 5. New capability

Payment authority that cannot exist before finality. The release instruction is
a protocol delivery from the deciding transaction. No reader, timer, caller or
agent can produce it early.

## 6. One invariant

**I1 Delivery.** Value leaves the vault only inside a transaction whose
`sender_address` is the bound gate and which was created by an `on='finalized'`
emission.

## 7. One failure mode

**Stranded value (E4b).** Moving authority onto delivery creates a failure v1 did not
have: if the finalized child fails or never arrives, the escrow has no path out.
Closed by I9 to I11: a clock may only return value to the funder, never release it.
