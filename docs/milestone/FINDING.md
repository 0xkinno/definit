# Finding: v0 released against a decision that was still appealable

Generated by `node scripts/gen-discovery.mjs`. Phase 4 adds the v1 side of the comparison.

## Method

v0 is deployed unchanged from commit b903f94. One action is driven through
adjudication and escrow. After v0's own 120 second window, the decision contract
is asked to promote the decision. While the promotion transaction's own lifecycle
still reads Accepted (not yet finalizable), the funder calls the vault's `settle`.

## Raw timeline

- promotion transaction lifecycle at the moment the settle was sent: Accepted, resolutionAction NoOp
- promotion appeal deadline (protocol): 1792238362
- settle decided at: 1792238350
- settle execution result: FINISHED_WITH_RETURN
- vault receipt status: SETTLED
- the settle was decided 12 second(s) before the promotion's appeal deadline

Raw records: `docs/evidence/milestone/spike/e6-h1-v0-run1.json` (the first run, in which the simulation of settle failed and no settle was sent; the vault was released by v0's own gate message after promotion finality) and `docs/evidence/milestone/spike/e6-h1-v0-run2.json`.

## Interpretation

The v0 vault accepted a release request from the funder while the decision it read
was still inside its protocol appeal window. That is the gap the milestone sets out
to close.

## What this does and does not prove

It shows the v0 design permitted a release before protocol finality of the thing it
depended on. It does not show an appeal overturning the decision: no overturn was
engineered or observed, and none is claimed. Whether such a release could later be
unwound by a recomputation (hypothesis H1) is not tested here. The v0 vault's own
transfer is emitted on the finalized stage of the settle transaction, which in this
run finalized after the promotion window closed. The finding is about authority, not
about a loss.

## The v1 side

The same attempt against v1 cannot be constructed: the v1 vault has no public method that releases on a caller's request, and every method that can send value to the recipient requires the bound gate as sender. This is asserted by `test_nobody_but_the_funder_can_release`-style tests and by the corpus case `i1-release-by-funder`, and recorded in `docs/evidence/milestone/h1-differential.json`.

## Other measured findings that shaped the build

- **Studio-dev does not credit transfers a contract emits.** A standalone payer contract showed the transfer message finalize with `value_credited: false` and no balance change in either stage form (`docs/evidence/milestone/transfer-credit-probe.json`). v1's evidence is therefore the emitted finalized-stage transfer message plus the vault's state and receipt.
- **A finalized message is a child transaction created at the appeal deadline** of the deciding decision, with the emitting contract as sender, in every recorded decision (`npm run spike`, twice).
- **Accepted-stage emission raises an execution error** under the pinned runner, so run R4 (a provisional storm) could not be produced.
- **A funded child that fails at execution leaves its parent successful and its effect unapplied** (spike E4b), which is why the vault has funder-only return paths.
